# 004 · Context Window（上下文窗口）

## ① 英文术语
Context Window

## ② 中文翻译
上下文窗口

## ③ 一句话定义
上下文窗口是模型在「一次生成」里能同时「看见」并用来做判断的输入＋输出总量的上限，通常以 token 数来衡量。

## ④ 核心知识

### 1. 它到底是什么：模型的工作记忆

你可以把大语言模型想象成一个读书极快、但记性有硬上限的人。你跟它对话时，它其实不是「真的记得你们之前聊过什么」，而是每一次生成时，系统都会把你和它**之前所有的对话原文**重新塞进它的眼前，让它「重新读一遍」再接着写下一句。

「重新读一遍」能读多少，就是这个模型的**上下文窗口**。它是一条硬性的物理边界：塞进来的历史超过了窗口，模型就「看不见」超出的部分了——不是它偷懒，是它的注意力机制根本算不到那里。

所以，上下文窗口本质上就是**模型单次推理时的工作记忆容量**。记住这个直觉：模型没有「长期记忆」，只有「每次现读现用的短期记忆」，而这个短期记忆的大小就是上下文窗口。

### 2. 为什么会有这个限制：Attention 的平方复杂度

这个限制不是产品经理拍脑袋定的，是架构决定的。

今天几乎所有大模型都基于 Transformer，而 Transformer 的核心机制叫 **自注意力（Self-Attention）**。它的妙处在于：让序列里**任意两个位置都能直接互相「看」**，从而捕捉长距离依赖。

但代价是：如果有 n 个 token，注意力矩阵就是 n × n。这意味着**计算量和显存占用随序列长度呈平方增长（O(n²)）**。序列翻一倍，注意力计算量变四倍。

这就是为什么早期模型的窗口那么小：

- **2018 年，GPT-1**：512 token
- **2019 年，GPT-2**：1024 token
- **2020 年，GPT-3**：2048 token

对比现在动辄几十万、上百万 token 的窗口，早期的模型几乎「看不了几段话」。这个限制一直到最近几年才被工程上的各种优化逐步突破。

### 3. 关键概念：它到底数的是什么

上下文窗口通常按 **token** 算，而不是按「字数」或「词数」算（token 的定义见第 3 讲）。这里有几个必须分清的易混点：

- **输入窗口 + 输出窗口**：总窗口通常被切成两块——一部分留给你的输入（prompt 历史），一部分留给模型的输出。所以你会看到 API 文档里出现 `max_tokens`（或 `max_completion_tokens`）这样的参数，它限制的是**输出**最多能写多长；剩下的才是输入能用的额度。
- **「支持」不等于「用好」**：即便窗口有 128K，模型对**中间部分**（所谓「lost in the middle」）的注意力往往最弱。论文 *Lost in the Middle*（Liu et al., 2023）就发现：把关键信息放在开头或结尾，模型记得最牢；放在长文档正中间，很容易被忽略。
- **窗口 ≠ 记忆持久化**：关了窗口（或开新会话），这段「短期记忆」就没了。想让模型长期记住，得靠 RAG、向量数据库、外部存储这些手段（后面几讲会讲）。

### 4. 历史脉络：从 512 到百万 token 的军备竞赛

上下文窗口的扩张，是近几年大模型竞争的一条明线：

| 时间 | 模型 | 上下文窗口 |
| --- | --- | --- |
| 2018 | GPT-1 | 512 |
| 2019 | GPT-2 | 1024 |
| 2020 | GPT-3 | 2048 |
| 2022 | GPT-3.5 时代 | 4K–8K |
| 2023 | GPT-4（初版） | 8K–32K |
| 2023 | Claude 2 | 100K |
| 2023 末 | GPT-4 Turbo | 128K |
| 2024 初 | Gemini 1.5 | 100 万+（宣称 1000 万） |
| 2024–2025 | 各家旗舰 | 普遍 128K–200K，长文本版到 100 万 |

推动这次大跃进的，主要是工程技巧而非重新发明架构，例如：

- **RoPE（旋转位置编码）**：让位置信息可以用旋转矩阵表示，支持**外推**到训练时没见过的更长序列。
- **FlashAttention**：优化注意力计算的内存读写模式，大幅降低显存占用，让长序列训练/推理变得可行。
- **稀疏/滑动窗口注意力**、**分块计算**等，都是绕开 O(n²) 的取巧办法。

### 5. 前沿进展：长上下文正在改变模型的工作方式

长窗口带来的不只是「能读更长的书」，而是范式的变化：

- **「把整本手册塞进上下文」**：以前必须靠微调或 RAG 才能让模型懂特定领域知识，现在可以直接把几十万字的文档整段丢进去，让模型现读现答。
- **Agent 工作流的基础**：智能体（Agent）要自己规划、调用工具、回看结果，每一步都要把历史结果放进上下文，窗口越大，它能连续干的事越多。
- **但长上下文不等于长记忆**：注意力在超长序列上的「检索」能力仍有衰减，业界还在争论「到底是真的长记忆，还是只是『没丢』」。同时，长上下文意味着**更慢的响应、更高的成本**，因为每次都要重新算那一大段历史。

一句话总结前沿判断：**窗口在变大，但「如何高效地使用窗口」比「窗口本身多大」更重要。**

## ⑤ 实际场景

你几乎每天都在碰到它，只是没意识到：

1. **聊着聊着模型「失忆」了**：多轮对话里，聊到后面模型突然忘了你开头说过的话——因为早期内容被挤出窗口了。
2. **API 报错 `context length exceeded` / `maximum context length`**：你粘贴的文章太长，或者历史太多，超出了模型窗口，调用直接失败。
3. **长文档总结**：把一篇几十页的报告丢给模型让它总结，能不能一次读完，取决于窗口够不够大；不够大就得先切块。
4. **写代码时**：让模型看一整个代码仓库，文件越多越容易超窗口，这时就要靠 RAG 或精简上下文。

## ⑥ 关联术语

- **Token（第 3 讲）**：上下文窗口的计量单位，先搞清楚 token 才能理解窗口数字。
- **RAG 检索增强生成（第 6 讲）**：当窗口装不下全部资料时，用它「按需检索」只喂相关内容，是绕开窗口限制的主流方案。
