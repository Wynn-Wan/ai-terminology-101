# 003 · Token（词元 / 令牌）

## ① 英文术语

Token

## ② 中文翻译

词元 / 令牌

## ③ 一句话定义

Token 是语言模型处理文本时的最小计量单位——模型不是按"一个汉字"或"一个单词"读文本，而是把文本切成一个个 Token，再让模型逐个去"猜"下一个 Token。

## ④ 核心知识

### 1. 一句话先讲清它是什么

你给 ChatGPT 发一句话，后台并不是把这句话原样塞进神经网络。系统会先经过一个叫**分词器（Tokenizer）**的组件，把句子打散成一小块一小块，每一小块就是一个 Token。然后每个 Token 会被映射成一个数字编号（ID），模型实际吃进去的是这一串数字，不是文字本身。

举个中文例子，句子"我喜欢大语言模型"可能会被切成：

```
我 / 喜欢 / 大 / 语言 / 模型
```

大约是 5 个 Token（实际切分取决于具体分词器，中文字符通常 1 字 ≈ 1~2 个 Token）。英文里，"I love language models" 大概会被切成 `I` / ` love` / ` language` / ` models` 这样的几块。

关键点：**Token 是"处理单位"，不是"字"也不是"词"。** 它介于两者之间，是分词器算法决定的、带统计意义的文本片段。

### 2. 为什么要用 Token 而不是直接用字或词

这是个好问题，答案是"两难之间的折中"。

- 如果按**单个字符**处理：中文有上万个常用汉字，英文只有 26 个字母，但按字符切分会让序列变得极长，"一句话"变成"几百个单位"，模型算起来又慢又难抓住词义。
- 如果按**完整单词**处理：词汇表会爆炸。光是英文就有几十万个词，加上各种变形（run / running / ran）、专业术语、网络新词、还有 Emoji 和代码符号，词表根本列不完，遇到没见过的新词（OOV，Out-Of-Vocabulary）就卡死。

Token 用了一个巧妙办法：**子词切分（Subword Tokenization）**。它把高频的常用词整个保留成一个 Token，把低频或生僻词拆成更小的、可以复用的片段。这样既控制住了词汇表大小（通常几万到十几万），又几乎不会遇到"不认识"的情况——因为任何文本都能用这套片段拼出来。

### 3. 主流分词算法：BPE 一家独大

现在绝大多数大模型（GPT 系列、Llama 系列、Mistral 等）用的是 **BPE（Byte Pair Encoding，字节对编码）**，或者它的变体。

BPE 的思路非常简单，可以理解为"最频繁的一对相邻字符，就合并成一个新符号"，反复迭代：

1. 一开始，词汇表里只有所有单字符（或单字节）。
2. 扫描整个训练语料，找出"出现频率最高的相邻符号对"（比如英文里 `t` 和 `h` 总是连着出现）。
3. 把这一对合并成一个新符号（`th`），加入词汇表。
4. 重复第 2、3 步几万次，直到词汇表达到预设大小（比如 5 万个）。

这样训练完之后，词汇表里就既有单个字符、又有 `th`、`ing`、`tion`、`the`、`token`、甚至整词。切分新文本时，用"贪心"策略：能匹配到的最长 Token 优先切出来。

BPE 的原始论文是 **Sennrich et al., 2016**（《Neural Machine Translation of Rare Words with Subword Units》），当时是为了解决机器翻译里的生僻词问题，后来被 GPT 系列发扬光大。OpenAI 用的 GPT 分词器是在 BPE 基础上做了字节级（Byte-level）改造，能无损处理任何 Unicode 字符、Emoji、甚至乱码。

> 顺带一提：Google 早期用的是 **WordPiece**（BERT 的分词器，思路类似但合并标准是"最大化训练语料似然"），还有 **Unigram**（SentencePiece 里的一种，T5、Llama 用它）。三家都是"子词切分"，只是细节不同。现在 OpenAI 的开源分词器叫 **tiktoken**，Llama 3/3.1 用的是 **tiktoken 风格的 BPE**。

### 4. Token 为什么重要：它是"计费单位"和"能力上限"

Token 在工程上有两个直接落地的作用，所以你必须懂它：

**（1）计费与算力消耗。** 几乎所有大模型 API 都按 Token 收费（输入 + 输出分开算）。你花的钱，本质是"处理了多少个 Token"。而模型的算力消耗，和 Token 数量大致成正比（更准确说是和"序列长度的平方"相关，见下一节）。

**（2）上下文窗口（Context Window）的度量。** 我们常听说"GPT-4 有 128K 上下文"，这个 128K 指的就是"最多能塞进 128,000 个 Token"。上下文窗口、Token 数量、计费，这三件事是绑在一起的。

一个实用的经验换算（不同模型略有差异）：**英文大约 1 个 Token ≈ 0.75 个单词，或者说 100 个 Token ≈ 75 个单词；中文大约 1 个汉字 ≈ 1~1.5 个 Token。** 所以"一段 3000 字的文章"大概就是几千个 Token，你就能心里有数它大概占多少窗口、花多少钱。

### 5. 一个隐藏的坑：Token ≠ 字符，中英文不一样

这个坑很影响成本，新手经常踩：

- 同一个意思，**英文通常比中文省 Token**（英文用字母组合，BPE 合并后效率高）。
- **中文一个字往往就是 1 个 Token 起步**，甚至生僻字、生僻组合会拆成 2~3 个 Token。
- 空格、标点、换行符，**也都占 Token**。
- 代码里的缩进、重复符号（比如 `=====`），会吃掉大量 Token。

所以如果你做产品要控成本，中文场景的 Token 消耗往往会比直觉上更高，这点要提前算清楚。

### 6. 更深一层：Token 怎么进入神经网络

想真正理解，可以记一条完整的"流水线"：

1. **分词（Tokenization）**：原始文本 → Token 序列。
2. **编号（Encoding）**：每个 Token 查词汇表，映射成唯一的整数 ID。
3. **嵌入（Embedding）**：每个 ID 再查一个"嵌入矩阵"，变成一个高维向量（比如 4096 维）。这个向量承载了该 Token 的语义信息。
4. **送入 Transformer**：这些向量一起进入 Transformer 的各层做计算，互相"看到"上下文。
5. **输出再映射回来**：模型最后输出一个"概率分布"，预测下一个最可能的 Token ID，再反查回文字。

所以你能看到一条清晰的分层：**文字 → Token → 数字 → 向量 → 计算 → 概率 → 再变回文字。** 理解这条链，LLM 的很多行为（为什么会有幻觉、为什么能续写、为什么能翻译）都变得好解释了。

### 7. 前沿进展与正在发生的变化

Token 这套机制也不是铁板一块，近年有几个值得关注的方向：

- **词汇表之争**：模型越大，词汇表设计越关键。词汇表太小 → 序列变长、成本变高；太大 → 每个 Token 学不透、容易浪费。各家的 Token 词汇表大小从 3 万到 15 万不等，是重要的架构选择。
- **多语言 Token 公平性**：因为 BPE 是在英文为主的数据上训练的，导致"英文更省 Token、其他语言更费"，这被研究者批评为"Token 层面的语言不公平"（Tokenization bias）。有论文专门讨论非英语用户成本更高的问题。
- **字节级模型（Byte-level models）**：像 Meta 的 MegaByte、以及一些新架构，想干脆跳过子词、直接按"字节"处理，彻底摆脱分词器这个"历史包袱"。虽然还没成为主流，但是个活跃方向。
- **上下文变长带来的成本革命**：随着窗口做到 128K、1M 甚至更大，Token 越多，注意力计算的平方级成本就越痛，于是催生了各种"稀疏注意力""线性注意力"来降低长序列成本——这些都和 Token 数量直接相关。

### 8. 一句话总结核心

Token 是 LLM 世界里的"原子单位"：分词器把文字切成 Token，模型猜下一个 Token，API 按 Token 收费，窗口按 Token 计量。搞懂 Token，就拿到了理解后面"上下文窗口""推理成本""计费"这些概念的钥匙。

## ⑤ 实际场景

- 你在 OpenAI / Claude / DeepSeek 等平台的**账单页**，看到的"tokens used"就是它。
- 你在代码里调用 API，报错说"context length exceeded"（超出上下文长度），本质就是你的输入 Token 数超了窗口上限。
- 你看到产品宣传"支持 128K 上下文"，心里能换算成"大概能塞进 8~10 万字中文"。
- 你写 Prompt 想让模型输出长文，设置 `max_tokens` 时，就是在限定它"最多生成多少个 Token"，少了会被截断。

## ⑥ 关联术语

- **Context Window（上下文窗口）**：以 Token 为单位的"模型记忆上限"，第 4 讲会细讲。
- **Embedding（嵌入）**：Token 变成的那个高维向量，是后续检索增强（RAG）的基石。
- **Inference（推理）**：模型"逐个猜下一个 Token"的运行过程，Token 数直接决定推理速度与成本。
