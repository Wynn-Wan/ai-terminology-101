# 026 · Function Calling / Tool Use（函数调用 / 工具调用）

> 第 26 讲 · 2026-09-16

---

## ② 中文翻译

函数调用 / 工具调用

## ③ 一句话定义

让大模型不只会"说话"，还能发出结构化的指令，去调用外部函数或工具（查数据库、调 API、改文件、控制设备），把拿到手的真实结果再组织成最终回答——相当于给大模型接上了一双能干活的手。

---

## ④ 核心知识

### 1. 为什么非要"工具调用"不可？

先认清一件事：**大语言模型（LLM）本质上是一台"预测下一个词"的机器**。它再聪明，也只能输出 token，不能真的去查数据库、不能真的发网络请求、不能真的改文件、不能真的关掉你家空调。它所有的"知识"都是训练时见过的文本，有截止日期；它的数学计算是"凭感觉拼字"而不是"确定性执行"。

这带来几个硬伤：

- **实时信息拿不到**：问"今天上海天气"或"我订单到哪了"，模型瞎编，因为它没有实时数据源。
- **确定性操作不可靠**：让模型"算 12345 × 67890"，它可能错；让它"精确地把某行数据写进系统"，它可能顺手改写别处。
- **无法真正作用于外部世界**：它只能给你文字建议，没法替你真正把邮件发出去、把票订上、把代码跑起来。

于是思路就出来了：**让模型只负责"决策 + 表达意图"，把"执行"交给外面的程序**。模型说"我要调用一个叫 `get_weather` 的函数，参数是上海"，宿主程序真的去调用，把结果塞回给模型，模型再组织语言回答。这就是 Function Calling / Tool Use。

### 2. 工作机制：一个标准的"代理循环"

工具调用不是模型自己在变魔术，它背后是一套固定的协作流程（常叫 **agentic loop**，代理循环）：

1. **声明工具**：开发者先把能用哪些工具告诉模型。每个工具包含三样东西——**名字**（如 `search_database`）、**自然语言描述**（"在订单库里按手机号查订单"）、**参数定义**（一个 JSON Schema，规定它要收哪些参数、每个参数什么类型、必填还是可选）。
2. **模型提议调用**：当用户问"我尾号 8888 的订单到哪了"，模型读懂了意图，但它不直接回答，而是输出一条**特殊格式的消息**——不是普通文字，而是一段结构化 JSON，比如 `{"name":"search_order","arguments":{"phone_tail":"8888"}}`。
3. **宿主拦截执行**：真正的"跑代码"这一步，模型根本不参与。是外面的程序（agent 运行时、你的应用后端）识别到这条工具调用消息，替它去执行函数、拿到真实结果。
4. **结果回填**：执行结果作为一条新消息追加进对话历史（通常标记为 role: "tool" 或 "function"），塞回给模型。
5. **模型组织回答**：模型看着工具返回的结果，再用自然语言说人话："您的订单已经到上海虹桥分拨中心，预计明天送达。"

关键要记住一句话：**模型只"提议"调用，绝不"亲自"执行**。这个分离，是安全和可控性的基石——外部的代码可以校验参数、加权限控制、记录日志、随时拒绝。

### 3. 几个必须搞懂的关键概念

- **工具声明 vs 工具执行**：声明是模型输入的一部分（占 token）；执行是宿主的事。模型永远碰不到你真正的执行权限。
- **JSON Schema 约束参数**：靠 Schema 逼模型把参数给对格式，减少"参数给错类型"的乱子。这也催生了后面的 Structured Outputs。
- **串行调用 vs 并行调用**：一次问话可能触发一个工具，也可能触发多个。多个工具之间若没有依赖，可以并行发出去（省时间）；若后一个要用前一个的结果，就得串行等。模型要学会判断依赖关系。
- **失败与重试**：工具执行可能报错（参数错、网络超时、权限不足）。好的设计会把错误信息原样喂回模型，让模型看错误、调整后再试——这本身就是一种"自我纠错"。
- **Token 成本**：工具描述和每次调用的结果，都要占上下文窗口。工具太多、描述太长，会又费钱又挤占空间，还可能让模型"选错工具"。所以工具清单要精、描述要准。

### 4. 历史脉络：从论文到产品

工具调用不是一夜冒出来的，它走过一条清晰的演化线：

- **2021 年 · WebGPT**（OpenAI）：让模型学会"上网搜索再回答"，是"模型 + 外部工具"的早期雏形。
- **2023 年 2 月 · Toolformer**（Meta AI）：论文《Language Models Can Teach Themselves to Use Tools》。核心想法很漂亮——**让模型自学什么时候该用工具**。做法是：在大量文本里自动插入 API 调用标记（计算器、搜索引擎、翻译器等），训练模型判断"这里该不该调 API、调哪个、传什么参数"。它证明了：不需要人类手把手标注，模型能自己学会"何时求助工具"。
- **2023 年 3 月 · ChatGPT Plugins**（OpenAI）：第一次把工具调用**产品化**推给大众，让 ChatGPT 能连外部服务（订机票、查天气、读文档）。
- **2023 年 6 月 · Function Calling API**（OpenAI）：在 `gpt-3.5-turbo-0613` / `gpt-4-0613` 上正式推出，开发者可以用 JSON Schema 描述函数、让模型输出结构化调用。这是工具调用走向**工程化、可量产**的标志性节点。
- **随后 · Anthropic Tool Use**：Claude 系列也推出对等能力，并逐渐成为 agent 开发的主流底座之一。
- **2024 年底 · MCP（Model Context Protocol）**（Anthropic 推出）：把"模型怎么连工具"这件事**标准化、开放化**，像 USB 接口一样，一个协议让各家模型都能接同一批工具服务器。这是当前最热的趋势之一。

### 5. 重要论文与人物

- **Tim Schick 等 ·《Toolformer: Language Models Can Teach Themselves to Use Tools》(2023)**：自学用工具的里程碑，把"工具调用"从人工设计变成模型可习得的能力。
- **姚顺雨（Shunyu Yao）等 ·《ReAct: Synergizing Reasoning and Acting in Language Models》(2022/2023)**：提出"推理（Reasoning）+ 行动（Acting）"交织——模型一边思考一边调用工具，而不是"先想完再动手"或"只动手不想"。这是 agent 工作流的重要思想源头。
- **Gorilla（UC Berkeley, 2023）**：专门研究模型如何准确生成 API 调用，减少"调错函数/给错参数"的幻觉。
- **HuggingGPT（Microsoft, 2023）**：让 GPT 当"大脑"，去调度 Hugging Face 上成千上万的现成模型当"工具"，展示了工具生态的想象力。

### 6. 前沿进展

- **MCP 标准化**：把工具连接的"协议层"统一起来，工具做一次、处处可用，正在成为 agent 生态的基础设施。
- **Structured Outputs / 严格 JSON**：模型能保证输出的 JSON 严格符合你给的 Schema（不只是"尽量"），让工具调用更可靠、少解析错误。
- **从"单次调用"到"长程 agent 工作流"**：现在的前沿是让模型在几十分钟、几十步里持续规划 + 调工具 + 纠错，完成一件复杂任务（比如"帮我调研竞品并写报告"）。
- **更丰富的工具类型**：浏览器自动化、本地代码执行、文件读写、甚至控制桌面/手机——工具不再只是"查个 API"，而是能真正操作系统。
- **安全与权限治理**：工具能力越强，越要管住"模型提议了什么、程序到底允不允许执行"，出现了权限白名单、人工审批、可审计日志等机制。

## ⑤ 实际场景

- **你天天在用的**：让 ChatGPT / Claude 查天气、订票、读邮件、搜网页，背后全是工具调用。
- **客服机器人**：用户问"我的订单呢"，模型调用订单查询系统，拿到真实物流再回答，而不是瞎编。
- **数据分析**：模型根据问题**生成 SQL 查询语句** → 程序执行 → 模型把查询结果解读成人话。
- **我（福金）自己**：我读写文件、搜网页、调 API、发消息，靠的就是一整套工具调用机制——你让我"改个文件"，我输出的其实是"调用 write 工具"的结构化指令，由运行时去执行。
- **编程助手**：Cursor / Copilot 里的"运行终端命令""读取代码库"，也是工具调用。

## ⑥ 关联术语

- **Agent（智能体）**：工具调用是 agent 的"手"，agent 是"会自己规划并反复调工具的模型 + 运行时"。后面第 30 讲的 AGI，往往也被描述成"能自主使用一切工具的通用智能"。
- **Structured Outputs / JSON Mode**：工具调用的可靠基础，保证模型输出的是机器能解析的结构化数据。
- **RAG（检索增强生成）**：RAG 里的"检索"这一步，现在常常就是通过"调一个检索工具"来实现的，两者经常搭着用。
