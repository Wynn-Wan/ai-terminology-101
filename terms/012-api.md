# 012 API (Application Programming Interface)

- ① 英文术语：**API (Application Programming Interface)**
- ② 中文翻译：**应用程序接口**（也常直接说「接口」或「API」）
- ③ 一句话定义：API 是两段程序之间约定好的一套「怎么喊我、我回你什么」的规则，让不同软件不用了解对方内部细节，就能互相调用、交换数据。

- ⑤ 实际场景
- ⑥ 关联术语

---

## 一句话定义

API（应用程序接口）是软件与软件之间的一套**契约**：它规定了「你用什么方式、发什么格式的请求，我会返回什么格式的结果」。你不需要知道对方内部是怎么实现的，只要照着契约调用，就能拿到想要的服务。

---

## 核心知识

### 1. 它本质是「抽象层」：把复杂性藏起来

「接口（Interface）」这个词，最原始的含义就是「两个东西之间的接触面」。你家的墙上有电源插座——你不用管电是怎么发出来、怎么变压、怎么走线到你家的，你只需要知道「插这个孔、能取到 220V 电」。插座就是一个「电力接口」。

API 在软件世界里干的是同一件事：把一大坨复杂的实现（数据库、算法、网络、权限……）**封装**起来，只对外暴露几个清晰的「入口」，并承诺这些入口的行为。调用方（客户端）只跟这个薄薄的面打交道，底层怎么改都行，只要契约不变，调用方就不用动。

这个思想在计算机科学里有个更早的名字叫**信息隐藏（information hiding）**，出自 David Parnas 1972 年的经典论文《On the Criteria To Be Used in Decomposing Systems into Modules》。Parnas 的核心主张是：模块之间应该只通过明确的接口交流，各自内部怎么实现是各自的事。API 就是这套思想在「程序与程序之间」的落地。

### 2. 历史脉络：从「函数调用」到「网络服务」

API 这个词很老，但它的形态一直在变：

- **最早**：库函数。你用 C 语言调 `printf()`，这就是最朴素的 API——函数签名就是契约。
- **1990 年代**：本地进程间通信，以及 CORBA、DCOM 这类「远程调用」技术想让人像调本地函数一样调远程对象，但太复杂，没流行开。
- **2000 年前后**：Web 兴起，出现了 **SOAP/XML-RPC**。它用 XML 把请求和响应包成信封，很「规范」但也很笨重。
- **2000 年**：Roy Fielding 在他的博士论文《Architectural Styles and the Design of Network-based Software Architectures》里提出了 **REST（Representational State Transfer）** 这套架构风格，主张「万物皆资源、用 URL 定位资源、用 HTTP 动词操作资源」。这是现代 Web API 的理论基石，也是绝大多数 AI 服务 API 的底层哲学。
- **2010 年代**：REST + JSON 成为绝对主流，简单、可读、跨语言。
- **最近几年**：出现了 gRPC（Google 出品，基于 HTTP/2 和 Protocol Buffers，追求高性能）、GraphQL（让客户端按需取字段）等新风格。
- **AI 时代**：几乎所有大模型能力都以 HTTP API 形式对外提供，OpenAI 的 API 设计（`/v1/chat/completions` 这种「聊天补全」端点）事实上成了行业标准。

### 3. 关键概念：一套 API 由什么组成

一个典型的 HTTP API（也是 AI API 的样子）由这几块拼成：

- **Endpoint（端点）**：一个 URL，代表一个具体的操作入口。比如 `https://api.openai.com/v1/chat/completions`。
- **HTTP 方法（动词）**：GET（读）、POST（提交数据/触发动作）、PUT/PATCH（改）、DELETE（删）。
- **请求（Request）**：客户端发过去的东西，通常包含 **请求头（Headers）** 和 **请求体（Body）**。AI 场景里，body 通常是 JSON，比如 `{"model": "gpt-4", "messages": [...]}`。
- **响应（Response）**：服务端回过来的东西，含 **状态码（Status Code）** 和响应体。200 表示成功，401 是没权限（鉴权失败），429 是「请求太频繁」，500 是服务器内部出错。写代码调 API 时，一半的功夫在处理这些状态码和异常。
- **鉴权（Authentication）**：怎么证明「你是你」。最常见是 API Key——一个长字符串，放在请求头里（如 `Authorization: Bearer sk-xxxx`）。Key 就相当于你家门的钥匙，泄露了别人就能花你的额度，所以要用 SecretRef 之类的机制保管，不写进明文日志。
- **序列化格式（Serialization）**：数据在网络上传输时得变成一串字节，最常见的是 JSON；gRPC 用更紧凑的二进制格式。

### 4. REST、RPC、GraphQL：三种风格一句话区分

- **REST**：面向「资源」。核心是名词（资源）用 URL 表示，动词（操作）用 HTTP 方法表示。直观、可缓存、生态最大。
- **RPC**：面向「动作」。核心是「我要调用某个函数」，比如 `getUser(id)`。gRPC 就是现代 RPC。调用起来更像本地函数，性能好，但耦合略高。
- **GraphQL**：面向「查询」。客户端写一段查询语句，精确声明「我只要这几个字段」，服务端就只回这几个。适合前端数据需求多变、想省流量的场景。

AI 领域的 API 主流是「REST 风格 + JSON 体」，但内部又带着点 RPC 的影子（`chat/completions` 本质是「帮我完成一次补全」这个动作）。

### 5. AI 领域的 API：一个行业的共识

2022 年 ChatGPT 爆火后，「模型即服务」成为主流商业模式。你不必自己买 GPU、训模型、部署推理，只要花钱调 API 就行。这背后有几个重要现象：

- **OpenAI 协议成为事实标准**：`/v1/chat/completions` 这个端点格式，被大量开源框架和竞品（如本地推理服务器 Ollama、vLLM 的 `--api` 模式）直接兼容。好处是：你写一套代码，换个模型供应商往往只要改 base URL 和 key。
- **流式响应（Streaming / SSE）**：大模型生成是逐字（逐 token）吐出来的。为了不让用户干等十几秒，API 采用 Server-Sent Events 流式返回，token 一个个蹦出来，像打字机。你调 API 时常见的 `stream: true` 就是开启这个。
- **Tool Calling / Function Calling**：API 不只是「聊天」，还能让你把自己的函数「登记」给它，让模型决定何时调用并生成参数。这把 API 从「问答接口」升级成「可编程的执行入口」。
- **MCP（Model Context Protocol）**：2024 年底由 Anthropic 提出，想给「模型如何调用外部工具/数据」立一个统一协议，被很多人看成「AI 界的 USB-C 接口」。这是 API 思想在 AI 时代的最新进化方向。

### 6. 重要论文与人物速记

- **David Parnas（1972）**：模块化与信息隐藏，接口思想的源头。
- **Roy Fielding（2000）**：REST 博士论文，现代 Web API 理论奠基人。
- **Tim Berners-Lee**：发明万维网，HTTP/URL 这套 API 的「物理底座」都是他定义的。
- 前沿没有单点论文，但 **OpenAI 的 API 文档、Anthropic 的 MCP 规范**，是当下 AI API 事实上的「教科书」。

### 7. 前沿进展

- **API 即产品**：一批公司（Stripe 之于支付、Twilio 之于短信、OpenAI 之于模型）证明了一件事——把核心能力做成好用、好文档、稳定计费的 API，本身就是一门大生意。
- **OpenAPI 规范**：用一份 YAML/JSON 把整个 API 的端点、参数、返回结构描述清楚，机器能自动生成文档、客户端代码、测试用例。OpenAI、Anthropic 都公开了符合 OpenAPI 的 schema。
- **Agent 时代的 API**：当「智能体」要自己决定调哪个工具、怎么调时，API 的「可发现性」和「自描述」变得空前重要——模型是靠读 API 的文档/schema 来学会调用的。写清楚 API，某种意义上就是在「教」模型怎么用你。

## 实际场景

- 你在自己的应用里调用 ChatGPT、Claude、通义千问、DeepSeek 的能力——这就是在调 API。
- 你用 Python 写 `requests.post("https://api.openai.com/v1/chat/completions", ...)`，或装上官方 SDK（如 `openai` 包）——SDK 只是「把 API 调用包装成好用的函数」的糖衣。
- 你让本地跑一个 Ollama，然后用 `http://localhost:11434` 去请求——本机上的 HTTP 服务也是一个 API。
- 你在代码里收到 401（key 错了）、429（超频了）、超时——这些都是 API 的「响应」，读懂状态码就是调 API 的基本功。

## 关联术语

- **Function Calling / Tool Use（函数调用/工具调用）**：API 的「进阶版」——不是人手动写死调用，而是让模型按需自动调用你的 API。下一阶段会专门讲。
- **Latency（延迟）**：调一次 API 要等多久。模型 API 普遍「慢」，延迟优化是实际工程里的头等大事，后面会展开。
