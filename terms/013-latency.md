# 013 · Latency（延迟）

> 教学日期：2026-09-03

## ① 英文术语
Latency

## ② 中文翻译
延迟（在系统/网络语境里常被叫「时延」）

## ③ 一句话定义
延迟，指一个请求从「发出」到「开始收到响应」之间所花的时间；对 AI 应用来说，最直观的理解就是：你点下「发送」到屏幕上冒出第一个字，中间那一段等待。

## ④ 核心知识

### 4.1 先分清三个容易混的词：延迟、吞吐、响应时间

很多人把这三个混着说，但它们指的是三件不同的事，搞清楚之后你会发现性能优化这件事突然有了抓手。

- **延迟（Latency）**：一个任务「启动」到「出结果」的时间差。比如你发一条消息，到模型吐出第一个 token，这中间是延迟。
- **吞吐（Throughput）**：单位时间内能处理多少任务。比如「每秒能生成 200 个 token」，这是吞吐。
- **响应时间（Response Time）**：用户从发起请求到完整拿到结果的总时长，包含了排队等待 + 延迟 + 传输耗时。

一个很形象的类比：水管。延迟是「打开水龙头后，第一滴水多久才流出来」；吞吐是「每秒能流多少升水」。水管可以很粗（吞吐大）但很长（延迟高），也可以很短但很细。AI 服务里，这两个指标常常要互相妥协——你想让更多人同时用（吞吐优先），单个请求就可能要多等一会儿（延迟变差）。

### 4.2 生成式 AI 里，延迟为什么特别「疼」

传统软件（比如查数据库、算一个数字）的延迟通常以**毫秒**甚至**微秒**计，而且答案是一次性返回的。生成式大模型完全不同，它有两个天然拉高延迟的特性：

**第一，逐字生成（自回归）。** 大模型不是一次性把整段话「算」出来的，而是一个 token 一个 token 往外吐：先算出第一个字，再根据第一个字算第二个字，依此类推。所以「生成一句话」的总耗时，约等于「每生成一个 token 的时间 × token 数量」。这就是为什么长回答特别慢——不是开头慢，是整个过程被拉长了。

**第二，算力密集。** 每生成一个 token，都要把整个模型的权重跑一遍（后面讲 Transformer 和 GPU 时会展开）。模型越大，单 token 耗时越久。这带来一个经典指标：

> **TTFT（Time To First Token，首 token 延迟）**：从发请求到第一个 token 出现的时间。
> **TPOT（Time Per Output Token，单 token 生成时间）**：之后每个 token 平均花多久。

用户感知最敏锐的是 TTFT——如果点下去 3 秒还一个字没冒出来，人会觉得「卡了」。而 TPOT 决定了「打字机式」的流速。这两个指标现在是评估 LLM 服务的核心口径，你在 API 文档、论文、评测报告里会反复看到它们。

### 4.3 延迟到底「花」在哪了

把一个 AI 请求拆开，延迟大致由这几段组成，每一段都能单独优化：

1. **网络传输**：你的设备到服务器的物理距离、网络状况。跨洲请求比同城请求天然慢几十到几百毫秒。
2. **排队**：高峰期服务器忙，你的请求要排队等 GPU 空出来。
3. **预处理（prefill）**：把你的 prompt 一次性吃进去、算出内部状态。prompt 越长，这段越久——这也是为什么超长 prompt 会明显变慢。
4. **逐 token 生成（decode）**：上面说的自回归过程，是总时长的大头。
5. **后处理与回传**：格式整理、内容安全过滤、把结果发回给你。

所以「我输入了一大段背景资料，模型过了好一会儿才开始写」——慢在 prefill；「模型开始写了，但一个字一个字蹦得很慢」——慢在 decode。诊断问题的第一步，就是先分清慢在哪一段。

### 4.4 历史脉络：从「能不能用」到「快不快」

延迟这个词在计算机领域很老了，网络时代就存在（打电话、打游戏都讲究延迟）。但它在 AI 领域地位的变化，有一条清晰的线索：

- **研究阶段（2022 及以前）**：大家更关心「模型聪明不聪明」，延迟是次要问题。跑一个 demo 慢几秒，无所谓。
- **产品化阶段（2023 起，ChatGPT 之后）**：模型能力够用了，竞争焦点开始转向「体验」。ChatGPT 那个「逐字浮现」的设计，本身就是对延迟的一种心理补偿——与其让你干等 10 秒看一整段，不如 1 秒内先给你几个字，让等待「有东西可看」。这一招后来几乎成了行业标配。
- **实时交互阶段（2024 起）**：语音助手（实时对话）、AI 编程（Copilot 补全）、游戏 NPC 这些场景，把延迟要求压到了极致。语音对话如果延迟超过 ~500ms，人就会明显觉得「对方在犹豫」，对话自然度崩塌。于是整个行业开始「卷」延迟。

### 4.5 怎么把延迟降下来（前沿进展的方向）

这是现在工程界最热闹的战场之一，几个主流打法，你以后都会听到：

- **流式输出（Streaming）**：不攒整段，算出一个 token 就发一个。TTFT 大幅下降，用户「看到东西」的时间从「全部生成完」提前到「第一个 token」。这是所有 LLM API 的默认能力。
- **KV Cache 复用**：模型生成时，前面算过的内部状态（KV 缓存）可以缓存起来重复用，不用每次都从头算。尤其对多轮对话、长文档，能省掉大量重复计算。
- **投机解码（Speculative Decoding）**：让一个小模型「先猜」接下来几个 token，再用大模型一次性「验证」，猜对了就批量接受。本质是用「一个快模型打前站」来加速「慢模型」的逐字生成。
- **批处理（Batching）**：把多个用户的请求拼在一起同时算，提升 GPU 利用率（提高吞吐），但可能牺牲单个请求的延迟——这就是前面说的吞吐 vs 延迟的权衡。
- **量化与蒸馏**：把模型权重压缩（量化）、或让小模型学大模型（蒸馏），让同样一句话用更小的算力跑完，延迟自然降下来。
- **更快的硬件与推理框架**：专门的推理芯片、vLLM / TensorRT 这类推理引擎，在「怎么排布计算、怎么调度内存」上抠出大量时间。

你会发现一个规律：**延迟优化，本质是在「算得准」和「算得快」之间不断找新的平衡点。** 压缩得太狠，模型会变笨；完全不压缩，又慢得没法用。这个权衡，贯穿了后面要讲的 GPU、量化、推理等好几个术语。

## ⑤ 实际场景

你会在这里直接碰到延迟：

- **调 API 时**：看返回的响应，模型「吐字」的速度、第一段话多久出来，都是延迟的直接体现。官方文档通常会标「TTFT」和「吞吐」指标。
- **写 AI 应用时**：用户抱怨「点了没反应」或「回复太慢」，你排查的就是延迟。加个流式输出、缓存常见问题的答案、把 prompt 缩短，都是降延迟的手段。
- **语音 / 实时对话产品**：延迟直接决定产品能不能用。一个实时语音助手，延迟是硬指标，不是「锦上添花」。
- **AI 编程工具（Copilot、Cursor）**：代码补全必须快到「跟得上你打字」，延迟一高，体验立刻崩。
